# 개발 일지 - 2026-06-09

## 현재 프로젝트 방향

프로젝트의 핵심 목표는 단발성 replay 시연이 아니라, OmniGibson / BEHAVIOR-1K 기반 디지털 트윈 space에서 로봇 및 스마트홈 센싱 학습에 활용 가능한 고품질 데이터를 생성하는 프레임워크를 만드는 것이다.

최근 논의에서 replay 데이터는 발표용 동작 확인을 위한 보조 수단으로 정리했고, 장기 목표는 다음 흐름으로 재정의했다.

1. 디지털 트윈 scene에서 거주자 context, 센서 배치, 로봇 task, 카메라 관측을 구성한다.
2. episode 단위로 sensor / resident / robot / object / camera 데이터를 정렬해 저장한다.
3. 생성된 데이터의 품질과 다양성을 정량적으로 평가한다.
4. 이후 Cosmos 같은 world foundation model 기반 synthetic data augmentation 또는 visual domain variation으로 확장한다.

## 지금까지 구현된 내용

### OmniGibson 중심 실행 구조

- 기존 Electron 기반 모니터링 앱 중심 구조를 축소하고, OmniGibson / Isaac Sim viewport 안에서 직접 조작 및 시점 변경이 가능하도록 전환했다.
- 현재 viewport key mapping:
  - `1`: top overview camera
  - `2`: resident follow camera
  - `3`: free viewer camera
  - `C`: camera mode cycle
  - `W/A/S/D`: resident 이동
  - `Q/E`: resident follow 모드에서 회전
  - `F`: motion sensor range 표시 토글
  - `L`: sensor layout 순환
  - `K`: 현재 sensor layout export
  - `N`: randomized data-collection episode 시작
  - `T/Y`: task/replay placeholder trigger
  - `R`: reset scene

### Scene 및 robot 설정

- 기본 scene은 `Merom_0_int`를 사용한다.
- 내부 문은 제거한 doorless scene JSON을 사용한다.
- 정문은 보존하는 방향으로 scene export를 조정한 이력이 있다.
- 로봇은 현재 `R1Pro`를 사용한다.
- 로봇 초기 방향은 협업 기준에 맞춰 `-X / yaw 180 deg` 기준으로 설정했다.
- 약병 task object를 scene profile에 추가했고, HDF5 replay metadata의 object pose와 동기화하는 로직을 구현했다.

### Resident context 및 pose 다양화

`N` 입력 시 activity context를 선택하고, 해당 context에 맞는 resident 위치, 방향, posture, virtual sensor 값을 설정한다.

현재 주요 context:

- `arriving_home`
- `watching_tv`
- `resting_on_sofa`
- `playing_piano`
- `showering`
- `toilet_use`
- `sink_use`
- `resting_in_bedroom`
- `lying_in_bed`
- `bedroom_activity`
- `doing_laundry`
- `checking_laundry`

최근 조정한 pose / placement:

- `toilet_use`: 변기 좌표 기준으로 seated posture 배치.
- `lying_in_bed`: 침대 위치와 방향 기준으로 lying posture 배치. 팔 위치가 어깨 쪽으로 몰리는 문제를 수정했다.
- `playing_piano`: 피아노 의자 좌표 기준으로 seated/reaching posture를 적용하고, `-X` 방향을 바라보도록 조정했다.
- `showering`: 샤워 부스 내부 좌표 기준으로 이동하고, `-X` 방향을 바라보도록 조정했다.
- `loading_washer`: 로봇 작업 영역과 겹쳐 제거했다.

### Sensor layout 다양화

Motion sensor layout을 3종으로 구성했다.

- `current`: 현재 기준 배치. 피아노/카운터탑 영역 센서를 추가했다.
- `dense`: 기존 배치를 단순 확장하는 방식이 아니라, 더 많은 coverage를 목표로 독립적인 dense layout을 구성했다.
- `sparse`: 고정 4개 센서만 사용하는 낮은 coverage layout.
  - TV에서 소파 감지
  - 침대 쪽 감지
  - countertop 쪽에서 피아노 방향 감지
  - 세탁실 천장에서 세탁기 앞 감지

센서 관련 구현:

- 실행 중 `L` 키로 layout 전환.
- 실행 중 `F` 키로 range visualization 표시/숨김.
- 실행 중 `K` 키로 현재 active layout export.
- active sensor만 감지에 참여하도록 `SmartHomeSensorRig`을 수정.
- sensor prim을 viewport에서 직접 이동한 뒤 export할 수 있도록 stage transform sync 기능을 추가했다.
- sensor range 표시를 끌 때 잔상이 남는 문제를 줄이기 위한 render flush 처리를 추가했다.

### Episode 및 logging

현재 episode 시작과 step logging이 가능하다.

- `N` 입력 시 episode가 시작되고 context / resident / sensor 상태가 JSONL에 기록된다.
- replay 또는 task 실행 시 별도 run folder에 step log가 쌓이는 구조가 있다.
- snapshot에는 resident state, sensor layout, activity context, robot state, camera mode, virtual sensor 등이 포함된다.

현재 한계:

- episode schema가 아직 최종 학습 데이터셋 구조로 고정되어 있지 않다.
- camera frame 저장이 학습 데이터 수준으로 안정화되어 있지 않다.
- success/failure label이 자동으로 확정되지 않는다.
- object state 변화와 robot action/state의 timestamp alignment가 더 명확해야 한다.
- 데이터 품질 리포트가 자동 생성되지 않는다.

## Cosmos 연결에 대한 현재 판단

Cosmos는 프로젝트 목표와 방향이 맞다. 다만 지금 당장 붙이기 전에 우리 쪽 데이터셋 생성기가 먼저 정돈되어야 한다.

현재 판단:

- Cosmos는 장기적으로 visual realism, domain randomization, synthetic data augmentation에 적합하다.
- 하지만 Cosmos를 붙여도 action / state / object pose / success label / sensor reading이 정렬되어 있지 않으면 학습 가능한 데이터가 되기 어렵다.
- 따라서 우선 OmniGibson 내부에서 episode 단위 labeled multimodal dataset을 안정적으로 생성하는 구조가 필요하다.
- 그 다음 Cosmos 또는 Isaac Sim Replicator 기반 augmentation을 붙이는 순서가 현실적이다.

### Camera frame 저장 1차 구현

Episode run directory에 저주기 camera frame 저장 기능을 추가했다.

실행 옵션:

```bash
--save-camera-frames
--camera-log-fps 2.0
--camera-log-sources robot
--camera-log-width 640
--camera-log-quality 80
```

구현 내용:

- 기본값은 저장 비활성화이며, `--save-camera-frames`를 명시해야 JPEG 저장을 시작한다.
- robot camera frame은 robot RGB sensor에서 직접 가져와 `cameras/robot/`에 저장한다.
- top frame은 사용자가 보고 있는 viewer camera가 `overview` mode일 때만 `cameras/top/`에 저장한다.
- simulator frame 전체를 저장하지 않고 `camera-log-fps` 주기로 샘플링한다.
- `steps.jsonl`의 `dataset.camera_frames`에 이미지 파일 경로, frame id, sim time, 해상도, byte size를 기록한다.
- orphan frame을 피하기 위해 camera frame 저장은 `steps.jsonl` record를 쓰는 순간에만 수행한다.
- context initialization과 task trajectory를 구분하기 위해 `episode_phase`를 기록한다.
- camera frame은 `episode_phase == task_running`일 때만 저장한다. 따라서 `N`으로 context를 설정한 뒤 idle 상태에서는 이미지가 쌓이지 않고, `T`로 replay가 시작된 뒤부터 이미지가 저장된다.
- frame이 없는 경우도 `available=false`, `reason=...` 형태로 명시한다.
- `quality_report.json`에 source별 frame count와 missing frame ratio를 반영한다.

판단:

- 매 프레임 저장은 디스크 I/O와 저장 용량 부담이 커서 기본 방식으로 쓰지 않는다.
- 현재 권장값은 robot camera JPEG, 2 FPS, width 640, quality 80이다.
- 이 정도면 replay action/state/sensor log와 시각 관측을 정렬해서 "학습 가능한 multimodal episode dataset" 구조를 보여주기에 충분하다.

검증:

- Python compile 검증 통과.
- Isaac Sim Python 환경에서 RGB 배열을 JPEG로 저장하는 단위 테스트 통과.

### Robot camera 저장 방식 보정

처음 구현은 robot RGB sensor 중 첫 번째로 발견된 sensor 하나만 `cameras/robot/`에 저장했다.
이 방식은 로봇에 여러 RGB camera가 있을 때 어떤 camera stream인지 명시적으로 보장하지 못하고, dataset 관점에서도 multi-view 정렬이 불가능하다.

수정 내용:

- robot의 모든 RGB sensor를 탐색해 camera name 별로 저장하도록 변경했다.
- 저장 경로는 `cameras/robot/<camera_name>/episode_...jpg` 구조로 변경했다.
- `steps.jsonl`의 `dataset.camera_frames.robot`은 단일 frame 객체가 아니라 camera name을 key로 갖는 dict가 된다.
- 같은 step timestamp 안에 각 robot camera frame reference가 함께 기록되므로 multi-view observation으로 정렬된다.
- `manifest.json`의 `camera_logging`에 `robot_camera_mode: all_rgb_sensors`, `robot_camera_names`를 기록한다.

주의:

- 이미 수집된 기존 run은 단일 robot camera 저장 구조 그대로 유지된다.
- 새 구조를 검증하려면 OmniGibson 프로세스를 재시작해야 한다.

검증:

  - `robot_mpfyhw_left_realsense_link_Camera_0`
